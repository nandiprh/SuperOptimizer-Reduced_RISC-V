# Benchmark: enumeration vs adaptive MCMC vs HC-MCMC

This page compares the three search strategies, run **separately**, on targets
whose optimal instruction count is known by construction. The goal is not to
crown one winner: the benchmark identifies the region where each strategy
outperforms the other two.

The raw data is committed in
[`../results/search_benchmark.csv`](../results/search_benchmark.csv) and is
regenerated by `make bench-search`.

---

## 1. How to run

Build and run the full benchmark:

```bash
make clean && make
make bench-search
```

`make bench-search` is equivalent to:

```bash
python3 tools/benchmark_search.py \
    --budget 300000 --seeds 3 \
    --out results/search_benchmark.csv
```

Useful options:

| option | default | meaning |
|---|---|---|
| `--budget N` | 300000 | MCMC iterations for `adaptive` and `hc` |
| `--seeds N` | 3 | independent MCMC seeds per target |
| `--enum-max-len N` | 4 | enumeration cap (hard cap 4 in the C++) |
| `--enum-timeout S` | 8 | enumeration wall-clock limit before marking intractable |
| `--quick` | off | smaller suite (`multi 1..5`, `padded 0..20`) |
| `--out FILE` | `results/search_benchmark.csv` | raw per-run CSV |

Run the three strategies by hand on one target:

```bash
./superopt bench/toy/divergence.sopt --algo enum     --enum-max-len 4
./superopt bench/toy/divergence.sopt --algo adaptive --iters 300000 --beta 2
./superopt bench/toy/divergence.sopt --algo hc       --iters 300000
```

Each command prints a leading `algo=` field:

```text
algo=adaptive best_cost=1 best_eq=0 best_perf=1 best_insns=1 time=0.35
```

- `best_eq=0` means a correct program was found on the search tests.
- `best_insns` is the instruction count (the optimum for these targets).
- `time` is the wall-clock seconds of that run.

## 2. Target families with provable optima

All targets are generated by `tools/benchmark_search.py`; no ground-truth
solver is needed because the optimum is provable.

### `multi N` — required search depth

```text
live_in:  {a0, ..., a(N-1)}
live_out: {a0, ..., a(N-1)}
code:
  slli a0, a0, 1
  ...
  slli a(N-1), a(N-1), 1
```

Every live-out must be written by a distinct instruction, and the target uses
exactly one instruction per live-out. Therefore the optimum is exactly `N`
instructions. Increasing `N` increases the **depth** of the solution the search
must discover.

### `padded P` — buffer/target length

```text
live_in:  {a0, a1}
live_out: {a0}
code:
  <P instructions of algebraic identity gadgets on t0>
  add a0, t0, t0
```

The identity gadgets cancel algebraically, so the optimum is exactly **1**
instruction (`add a0,a0,a0` or `slli a0,a0,1`) regardless of `P`. Increasing
`P` increases the **buffer length** the MCMC has to search, without making the
solution deeper. Enumeration is unaffected because it stops at the first correct
program of length 1.

## 3. Metrics

For each run:

```text
success   = 1[ best_eq = 0 ]                    correct program found
optimal   = 1[ best_eq = 0 ∧ best_insns = opt ]  known optimum found
time      = wall-clock seconds
```

Success/optimality are reported as rates over the seeds. Enumeration is
deterministic, so it is run once per target; MCMC runs once per seed. Runs
marked `timeout` in the table are enumeration runs that exceeded
`--enum-timeout`.

## 5. Where each method performs better than the others

These are the points the benchmark actually measures; each statement is backed
by the tables above.

### Enumeration wins: shallow solution (`N ≤ 2`) or any shallow `padded` target

When the shortest correct program is 1–2 instructions, enumeration is exact and
orders of magnitude faster:

- `multi 2`: enum **0.000s**, HC 0.342s, adaptive 0.376s — all three optimal.
- Every `padded P`: enum **0.000s** and 3/3 optimal, while MCMC needs
  0.25–2.9s.

The enumeration search space is `Θ(B^{ℓ*})`; for `ℓ* ≤ 2` it is tiny. This is
also why enumeration is the right ground-truth oracle for short toy targets.

### HC-MCMC wins: required depth exactly 3 (and long shallow buffers among MCMC)

At `multi 3`, all three methods find the optimum, but HC-MCMC is fastest:

- enum 1.361s, **HC 0.717s**, adaptive 0.830s.

The crossover happens here because enumeration has to exhaust the enormous
length-3 space, while greedy HC-MCMC finds the three independent writes almost
immediately. HC-MCMC also beats adaptive MCMC on long shallow buffers with
`P = 20–24`: both reach 1/1 in HC's column, while adaptive misses one seed
(0.67 success/optimality).

### Adaptive MCMC wins: deep solution (`N ≥ 5`)

Once the required program is longer than the enumeration cap and greedy search
starts hitting local minima, adaptive temperature dominates:

- `multi 5`: adaptive **1.00** vs HC 0.33.
- `multi 6`, `multi 8`: adaptive **1.00** vs HC 0.00.
- `multi 7`: adaptive **0.67** vs HC 0.00.

At `multi 4` all MCMC variants still succeed and enumeration times out, so the
enumeration → MCMC crossing is at required depth 4; the HC → adaptive crossing
is at depth 5.

### Enumeration wins again: long target, shallow solution

On `padded P` the optimum stays at 1 instruction while the target grows to 31
instructions. Enumeration still returns the optimum in ~0s at every `P`, while
both MCMC variants slow down to 2–3s and eventually lose reliability:

- at `P = 28`, HC finds the optimum on 1/3 seeds, adaptive on 1/3;
- at `P = 30`, HC succeeds on 1/3, adaptive on 0/3;
- enumeration is 3/3 at every `P`.

This is the opposite breaking point: a long *buffer* hurts the random walk even
when the *solution* is shallow.

## 6. Practical decision guide

| Situation | Best choice | Why |
|---|---|---|
| Shortest correct program is known/expected to be ≤ 2 instructions | `--algo enum` | exact and ~0s |
| Required depth 3, and you care about wall time | `--algo hc` | all methods optimal; HC fastest |
| Required depth ≥ 4 | `--algo adaptive` (or `hc` at depth 4) | enumeration times out; adaptive has the best deep-search success |
| Long target, shallow optimum, and `ℓ* ≤ enum-max-len` | `--algo enum` | exact, independent of target length |
| Long target, shallow optimum, `ℓ* > enum-max-len`, very long buffer (`P ≥ 28`) | `--algo hc` among MCMC | higher success rate than adaptive at the extreme buffer lengths measured here |
| Long target, deep optimum | `--algo adaptive` | best optimality on deep searches |

No single strategy wins everywhere. The benchmark's summary is a boundary, not
a ranking:

```text
        shallow / short                 deep / long
enum    wins (exact, fastest)            loses (exponential / hard cap)
HC      wins at depth 3                  loses to adaptive at depth >= 5
adaptive competitive at depth 4          wins at depth 5..8
```

For the raw per-seed data, inspect
[`../results/search_benchmark.csv`](../results/search_benchmark.csv).
